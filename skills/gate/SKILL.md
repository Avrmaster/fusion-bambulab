# The print gate

A rule that lives only in prose gets forgotten, and the print pays for it. The gate holds the rules in a registry, finds the parts by itself, runs the checks, and writes a **stamp** for each geometry that passed.

**A part is checked only when its stamp exists.** A report, a printed table, a "TOTAL 0" from another script, or your own reading of the model is not a pass. Say "checked" only for a part whose stamp was written for its present geometry.

The gate is in a project when `gate/project.json` exists. Its one command is `python3 gate/tools/gate.py`, run from the project root. Without that file this skill does not apply; `python3 ${CLAUDE_PLUGIN_ROOT}/tools/setup_project.py <dir> --gate` adds it (see "Adding the gate" below).

## Exit codes

Every sub-command ends with one of these. Read the code, not only the text.

| Code | Meaning | What you do |
|---|---|---|
| 0 | pass | go on |
| 1 | open findings that block, or checks that could not decide | fix what failed, in the fix order of each rule. When the run says "nothing failed", nothing in the model is known to be wrong: do what each `NOT_RUN` row says, then run again |
| 2 | questions are open | answer them honestly (`attest list`) |
| 3 | more calls needed; the last line is `NEXT n/m` | run the same command again, until it is not 3 |
| 4 | the gate could not run: no project, a broken file, a parameter error, Fusion not answering, a forked copy, several declared targets and none named | repair the cause; `gate.py doctor` names it. Never treat 4 as "nothing found" |

A check that did not run is listed as `NOT_RUN`. It counts as open, never as passed. A part whose open rows are all `NOT_RUN` has the verdict `incomplete`, not `fail`.

The first line of a run gives the counts by verdict: `3 parts, 14 open (2 FAIL, 6 BLOCKED, 5 GROW, 1 NOT_RUN), 4 questions (2 answered by facts), 1 not run -> exit 1`. Under it, equal rows of a part are one line (`x6`, the first id, `+5 more`), what is measured and wrong first. Read those lines; the report holds every row.

## Before a change

1. `python3 gate/tools/gate.py status`. It needs no Fusion. It shows open findings, open questions, the parts in three states (`changed, not checked`: something the part's checks read changed since they ran, with why; `checked, no stamp`; `stamped`), how many units are to be measured again and about how long, and STLs without a valid stamp. Its counts are as of the last scan, whose time it prints: an edit in Fusion since is seen by the next scan, run or export. `verify` says the same about the stamps it checks. It exits 1 while a finding is open, a changed part was not checked, or an STL in a registered folder has no valid stamp. The same digest is printed at session start.
2. Read the rules of the area you will touch, with this project's numbers: `gate/RULES.md`, or `python3 gate/tools/gate.py rules --category inserts`. The `print-design` skill carries the same rules with the default numbers.
3. Before a hole, a pocket, a seat or a mating face moves: read the print ledger for the part and its mates, `python3 bambulab/tools/ledger.py status "<object>"` and `may-change "<object>"`. The ledger knows a part by the name of its object in the .3mf (`Bracket`), not by its gate part id (`demo/bracket`). A part with no record counts as printed: a `never` or a `FREE` whose reason is "no evidence" is no record, and exit 0 there is not a permission. Only the owner's recorded `not-printed` frees the part: ask him and record his words before the interface moves.
4. Say which parts you intend to change. You will pass them to the run.

## After a change

```bash
python3 gate/tools/gate.py run --changed --parts demo/bracket,demo/cover
```

- `--parts` is the intent: the parts you meant to change. A part whose geometry changed outside that list is a finding. A hole or pocket that vanished from a part is a finding too.
- The run talks to Fusion in short calls and stops at its wall time. Exit 3 is normal: call it again. Do not replace it with a long script of your own.
- The run measures only what changed. Each unit (one probe on one part) stores what it read: the regions of the document it looked at with every body in them (signature, place, shape, name), the parameters, tables and job keys it asked for, and the text of the probe. After the scan a unit runs again only when one of these changed: its own part, a neighbour it read (moved, changed, renamed, new, gone), a parameter it read, or the probe. The other units keep their facts, stamp or no stamp, and their parts are still reported. So one edit costs the units of that part and of the neighbours that read it, a change of nothing costs a scan, and a moved neighbour that can close a hole of a stamped part opens that part's check again (its stamp goes stale until the run measured it). The first run after an update to this version measures everything once: facts measured before it hold no record of what they read. `run --all --fresh` measures every unit again on purpose.
- What else measures units again, and why: an update of the plugin that changes the code of a probe or of `_geom.py`, `_geom_rings.py` or `_fusion.py` (comments and docstrings do not count), every unit of that code; an update of Fusion itself (the scan reads its version), every unit; a look a probe cut short for time (`screws_cut`, a late screw row), that unit. Regenerating ref occurrences (a hardware script that deletes and adds the screws at the same places) or renaming them re-checks every unit whose region holds them: their keys changed. Leave generated hardware in place when nothing about it changed.
- Visibility changes nothing. No probe reads a light bulb: a hidden part or ref is a neighbour like a shown one (a collision or a closed hole behind it is still found), and hiding or showing measures nothing again and kills no stamp. A body is left out only by an explicit rule: `not_printed` (by name) and `access.overlay_pattern` (by name, in the judges). A leftover tool body that is no part needs a name `not_printed` matches; its light bulb makes nothing a ref.
- Two records of what a unit read. "wide" is the box round all a probe could look at (as 0.3.2). fusion_near, fusion_gap and fusion_screws also note a "tight" one: only the kinds a probe lists, only other motion groups, the points a screw row asked and the boxes it chose its bodies by. `gate/project.json` `"deps"` (the owner's) says which decides: `wide` (the default) or `tight`. Under `wide`, every unit that only the wide record measures again is compared with its facts before, in `gate/run/<run>/deps_shadow.jsonl`, and the run says how many gave the same facts. Any difference is a violation: report it. The owner switches to `tight` with a bundle entry `{"kind": "deps", "deps": "tight"}`, refused while the shadow record holds a violation, nothing, or no unit with the same facts for one of the probes with tight regions (it names them). `gate.py status` says how many units are to be measured again and about how long that is in Fusion.
- A ref (a bought or hardware body) counts as changed when its faces changed, not only its outline: a hole that moves inside a bought plate re-checks the parts next to it.
- Short units share a call: a unit whose last measurement took a few seconds starts in what is left of a call, with that as its deadline, and the short units of one part (up to 3 s each by their last measurement, never the census) go into ONE Fusion call, each in its own namespace, each with its own result file. A unit that took most of a call or several calls still gets a call of its own. `gate/layout.json` `"fusion": {"batch": false}` sends every unit alone.
- A run scans in full only when something changed: one short pulse call per document (occurrence paths and transforms, every body's revision id, face count, volume and area, mesh nodes and triangles, linked documents; never the light bulbs and never the saved version, which an unsaved edit does not change) is compared with the pulse the last one-call scan read. `gate.py scan` and `run --fresh` always scan in full.
- When the units of a plan were measured over several calls, the call that finishes them scans once more and measures what changed in Fusion while the run went on; when that fits into what is left of the call (a pulse, or a scan known to be short) it is done in the same call, else that call exits 3 with `NEXT 0/1` and "the next call scans once more". It usually sends no unit. A run is never 0 on a census older than its last unit.
- A unit given up over its budget (`OVER BUDGET ... NOT RUN`) stays given up, with its `NOT_RUN` row, until something of the document, its inputs or its probe changes; it is not sent again on every run. `run --part ID --fresh` tries it again.
- For the long first run, loop in one background command instead of calling it by hand 300 times: `until python3 gate/tools/gate.py run --changed --for <key>; c=$?; [ $c -ne 3 ]; do :; done` (in a project with one target leave out `--for`). Read its last report with `report --last` when it ends.
- A document that is not open is `unreachable`: its parts keep their old stamps and get no new one. Open the document; do not skip the part.
- A run starts with a scan. A finished scan prints notes about the whole document, once: `LINKED` (printed bodies that come from a linked document, and who judges them), `HINT` (parts that are probably bought: a few faces, or many equal bodies in one component) and `NO GROUP` (parts in no motion group). A hint excludes nothing: the owner adds a `not_printed` pattern or leaves the part. While a scan needs more calls it prints `scan: not finished` and no counts.
- A large body can take more than one call before a unit measures anything: the unit answers that it is still signing the body, and the same command goes on. That is exit 3, not an error.
- A unit that answers after the gate stopped waiting is not lost. The call that timed out exits 4. Run the same command again: while Fusion is still busy with that unit it exits 4 again and sends nothing; when the unit has written its result, the run reads it and goes on. A `scan` or `export` in between changes nothing about that. Never delete a file under `gate/run/` to "unblock" a run, and never send the unit by hand. When the exit 4 says that nothing listens at the endpoint, Fusion is not running: start it and run again.
- `OVER BUDGET` lines (in the output of `run` and `scan`, in `status`, `doctor` and the report) name each call that worked longer than its unit's budget, each call that got no answer and left no result, and each unit that was given up after two such calls in a row (its rules are `NOT_RUN`, the run goes on and exits 1). Such a line is a defect of a probe, not a finding of the part: tell the owner, with the line, so it can be reported to the plugin. A `UNIT ERROR` line is the error text of a probe that ended a unit.
- An audit (`run --audit`) blocks nothing, with one exception: a part one of whose units was given up over its budget is not inherited. Nothing judged the rules of that unit, so the audit exits 1 and names the part; run it again (`run --part ID`) when the probe is fixed or the model is lighter.
- A note "the bodies round the part changed between two calls of this unit: ... is measured again from its start" means that a neighbour was edited while a unit was between two calls. That is right once. When a unit ends in the error "met other bodies than the call before in three calls in a row" and nobody edited the model, report it: a value read from Fusion is not stable.
- Facts are stored per geometry and judged again by today's judges. When a row says that the facts come from an older unit and the part is to be run again, do that (`run --part ID`): the judge does not guess from old facts.
- `python3 gate/tools/gate.py report --last` prints the last report again. Rows of one part with the same rule, cause and neighbour are one block with the count and the places; the fix order of a rule is printed once. `gate/reports/<run>.json` holds every finding with its own id: a waiver is per feature.
- A project with several .3mf projects declares several targets. A part is judged for one of them (its layer height, the fits measured under it), so name it: `run --changed --for <key>`. Without `--for` such a run exits 4 and judges nothing. `export --for <key>` judges the stored facts again for its own target, so one run serves the export for every project (no shipped probe reads the target or a target parameter; a unit that did would be measured again for the other target, and the export says so).

The verdict of a part is summed by the tool from every stored check of its present geometry. Do not read a verdict off one call's output.

### The hooks keep you to it

With the plugin's hooks on (`hooks/hooks.json`), in a session whose folder is gated, and for every path of a gated project that a session of another folder writes:

- Every call that sends a writing script to Fusion (the Fusion MCP tools `fusion_mcp_execute` without `readOnly`, `fusion_mcp_update`, `fusion_mcp.py run ... --write`, anything that names the Fusion port 27182, a Python script file that does) leaves a mark in `gate/run/dirty.jsonl` before the call runs, so a call that fails or hangs half way is marked too. The turn does not end (Stop, SubagentStop) while a mark has no `run --changed` or `run --all` that started after it, asked Fusion (not `--offline`, not `--no-scan`, not `--audit`), came from this session and ended with 0, 1 or 2: the hook says the exact command. Exit 3 means call it again. Exit 4 lets the turn end with "NOT checked": say so to the owner. After three reminders in a row the turn ends anyway with a loud line, and those marks only get a reminder line from then on; nothing of it is a pass. A project whose vendored gate is older than 0.3.0 is never held: one line says its changes are NOT checked until `setup_project.py <dir> --update-tools`.
- A tool call that writes the gate's own state is refused: `gate/owner/**`, `gate/project.json`, `gate/stamps/**`, `gate/tools/**`, `gate/rules/**`, the gate's run files and tickets, the print ledger and its tools, `.claude-plugin/` of the project, the settings that hold the hooks, the plugin files under `~/.claude/plugins/`, `~/.claude.json`, the session transcripts; also `claude plugin disable|uninstall`, and `claude` started with `--setting-sources` or with `--settings` that touch the hooks. A Bash command is read the way bash reads it: every line, the bodies of `if` / `for`, `$( )` and backticks, comments dropped, `$VAR` from the command's own assignments; a folder target (`cp -r x gate`, `rsync -a x/ gate/`, `git checkout REV -- gate`, `git checkout .`, `git reset --hard`, `git stash`) counts for what lands in it. `gate/layout.json` may be edited with the Edit or Write tool only while every registered project, STL folder and document stays in it. Code run by an interpreter that names such a file (also as a path joined from pieces) and writes on the same line is refused too; one that only reads it and writes elsewhere gets a warning; output to stdout is no write.
- An STL or .3mf of the gated project written past the gate (`cp`, `mv`, a redirect, the Write tool, zip, unzip into an STL folder, the slicer CLI `--export-3mf`, an upload to the printer, a Fusion script with `exportManager` / `createSTLExportOptions` / `MeshCalculator`, an STL export or an `.stl` opened for writing) is refused in `enforce` mode and warned about in `observe` mode. STLs come from `gate.py export`, .3mf files from `bambu3mf.save`. In `enforce` mode a Fusion script named through a variable the hook cannot read is refused: name it by its full path.
- When a hook check itself fails or runs out of time, a call that touches the gate's files, a printed file, the settings or an owner command is refused ("call it again"); any other call goes on with one line that says it was not checked.
- Read-only commands, read-only Fusion calls and the gate's own commands are never stopped. The owner's own work in his editor, Fusion or Bambu Studio is not seen by any hook; the next guarded save and `verify` say what changed. The owner can switch the hooks of his project in `gate/project.json`: `"hooks": {"stop": false}` (no hold, a line instead) or `"hooks": {"pre_tool": "warn"}` (a refusal becomes a warning).

## Fixing a finding

Each finding has a rule, a part, a place, a measured value and the limit with its tag, and one of these verdicts:

| Verdict | Meaning |
|---|---|
| `FAIL` | under the hard floor of the rule, or plainly wrong |
| `GROW` | under the target, and there is free space: fix it |
| `BLOCKED` | under the target, and a named neighbour stops the fix: this goes to the owner |
| `NOT_RUN` | the check could not decide: run it, do not argue it away |
| `INFO` | told, never blocking |

**Fix in the order the rule registers.** The finding prints that order, `gate/RULES.md` holds it. Take step 1 unless you can say what stops it, then step 2, and so on. For a thin wall round a heat-set pocket the order is: make the whole wall or shoulder wider where the outline is free; move the pocket with its screw; a local boss only where the outline cannot move; blocked on every side, report it with what stops it. Do not jump to the smallest patch.

After the fix run the gate again. A fix moves other things: a relief cut moves the lead-in, a thicker wall can close a path.

Some rows are about what the gate could see, not about the part:

- **Hardware the gate did not recognise** (`hardware.recognised`, `NOT_RUN`). A name picks the candidates and the shape decides: a screw is a head on a shank of a table thread (one body, or a head body and a shank body in one component), a bearing is a ring of a table row, a washer a thin ring. A body that a name pattern picked and whose shape says otherwise is listed and not judged (a magnet in a component of screws; a clamp screw named after the bearing it clamps). A screw hole with a bought body on its axis that nothing recognised means that no screw rule looked at that hole: name the ref as what it is (thread and length, `M3x12`, or the word; `pin`, `dowel`), or ask the owner to set the ref pattern of the project (`params explain screws.ref_pattern`; the patterns for washers, inserts, nuts, bearings and motors are parameters too). Naming a ref so that it IS found is the fix; never rename one so that it is not.
- **Other parts in front of openings** (`access.hole_covered`, `access.screw_path`): ONE row and one question per part and rule, for every part that stands in front of its openings or of its screw heads: nearest first, each with its distance and what it covers. It asks the assembly order: free only if each of them is mounted later and comes off first. The row keeps its id while the same parts stand in front of the same openings, however far out; it is asked again, with the whole list, when a covering part joins or leaves, or comes to stand in front of another opening. A body inside a bought or linked assembly is named with that assembly (`Gearbox / Motor / Rotor`). The part itself in the path is a `FAIL` per feature. What sits in an opening by design is no cover: the screw in its hole, the bearing in its seat, the bought part or fastener that reaches into a slot or window. A mesh body or a printed neighbour inside a slot or window says nothing about what it is for: it is judged like any cover. A seat or screw hole of the census that has no opening row at an outer end was not measured: `NOT_RUN`, run the part again.
- **A mesh body in a path** is never a `FAIL`: a mesh has no exact shape. The row stays `NOT_RUN` until the mesh is a solid body. When the mesh is no part of the build (an old version laid over the model), only the owner can say so: he sets `access.overlay_pattern`.
- **A one-layer skin between a counterbore and its hole** is asked once (`access.bridge_layer`): a bridge layer that is opened at the bench, or a leftover skin. Answer from the model, and put the bench step into the build notes.
- **Insert pockets**: one pocket gives one row per cause. The row of `inserts.wall` names the wall beside the melt relief too; `inserts.wall_at_relief` has the row when the wall round the lead-in passes, or when a smaller relief of the table would fit. A relief wall that is thin for a reason of its own (thinner than the lead-in wall and the step between the two diameters explain: 0.2 mm towards the relief of the next pocket) is a second row, in `inserts.wall_at_relief`: the worst wall of a pocket is never only a text. A pocket that ends one relief depth short of its table row (its relief was cut later and the hole was not deepened) is a row of `inserts.pocket_shape` that names this cause; the owner decides the group once. A hole that holds an insert or a screw is never taken for a magnet pocket, whatever its diameter.
- **A ring that was not judged** (`bearings.holding`, `NOT_RUN`): a bearing whose model is off its table row (a 608 drawn 7.3 wide), a ring the bearing unit passed over, a body named like a bearing whose shape could not be read. Correct the model of the bought part or the table; a pin or a clamp screw named after a bearing is only told (`INFO`).
- **Bearings inside a bought assembly** (`bearings.holding`, `INFO`): a bearing that bought bodies hold and at whose rings no printed part stands, seats or clamps (the rollers inside a gearbox) is not the finding of a printed part beside it. One row tells how many and which, and names the mesh bodies near them (a part drawn as a mesh cannot be measured). A ring that a printed part holds, or stops short of, is judged for that part; a bearing that nothing touches at all stays a `FAIL`.
- **A washer over a slot** passes when it reaches at least `washers.slot_land_min` over each flank and its ring lies on material everywhere beside the slot. Over a slot nearly as wide as itself it fails.
- **Narrow faces** (`walls.thin_faces`): a flat of a chamfer or of a tooth flank and the bridge steps under a counterbore are told in one `INFO` row, not failed. Narrow faces that touch are one row for the place. Equal places that repeat round one axis (the teeth of a wheel, a spline, a knurl: twelve or more on one even division of a circle) are one row for the profile: one decision covers it, and a place that differs keeps its own row.
- **A gap along a screw** (`screws.shell_bears`): a gap that a bought body bridges (a bearing ring the two parts clamp between them: on one line along the screw both parts press on it) is the clamp room of that body: one `INFO` row names it. A bearing may also sit beside the gap, within 3 mm of it along the screw: a ring in a seat of one part, flush with its face, that a lip of the other part reaches across the gap to press; the row says "beside" and gives both distances, so look at the seat and the lip, not into the empty gap. On that line the load must cross the gap through the body or the part that presses it: a lip with air under it on the line, and a ring that one shell holds in a closed pocket above or below its own hollow, bridge nothing. Beside the gap only a bearing is taken: a seal, a cord or a block there is named in the `FAIL` text as passed over. A gap with nothing in it is a `FAIL` per screw. A body in the gap that only one part presses on (a ring in a bore with no shoulder behind it, a pin through both parts, a part that stops short of the body) closes nothing: one `FAIL` row for all the screws of the part across that gap, with what each part does to the body. Facts of an older screw unit do not say what stands in a gap: the `FAIL` stays and says to collect the facts again.
- **A thread that nothing receives** (`screws.engagement`, `FAIL` with 0 mm): the row names the hole, the part the thread ends in and what lies on that axis. Model the insert or the nut as a ref body, or name the body that is there so that its pattern matches. A head that bears on a bearing ring through its washer is not judged for plastic under it (`screws.under_head`).
- **A hole that only changed its class** (`regression.feature_lost`, `INFO`): the same hole with the same segments, called an insert pocket or a plain hole by another version of the tables or tools, is not lost. A hole whose segments changed, or that is gone, is asked as before. A through opening that moved or changed size a little (same shape, parallel axis, its old centre inside the new one) is asked as "changed", with what it is now and how far it moved, not as "gone".
- **A long straight channel in an insert band** (`inserts.pocket_shape`, `INFO` with a question): a straight through hole far longer than any pocket of its diameter (the key channel to a set screw of another part) is no pocket by its shape, so no wall, relief or floor rule judges it, while no insert ref lies inside it. The census measures where each body on the axis lies along it (`span`): an insert ref beyond the far end keeps it a channel, asked what it is for; one inside it makes it the straight pocket it is (every insert rule judges it); one of unknown place (an older census) is NOT_RUN and the other insert rules judge it.
- **A blind thread pilot too shallow for any thread** (a phasing marker, the socket of a spigot): no screw holds in it, so no key path or cap is judged for it. It is still asked once, as every thread pilot is (`inserts.no_tapped_plastic`).
- **A toothed ring whose chamfer joins every tooth** (`walls.thin_faces`): when the one region of touching faces turns onto itself tooth by tooth, it is the profile row of that wheel. One tooth that differs keeps the whole region one row.
- **Bridge steps with other faces touching them** (`walls.thin_faces`): the steps are counted as steps; the other faces (a step cut 0.01 below the floor) stay one place and are judged.
- **The floor of an insert pocket whose screw comes in at the mouth** (`access.hole_closed`, `INFO`): when the body behind the floor is the body the screw head bears on, standing at the mouth on the axis, nothing passes the floor (`inserts.floor` judges it).
- **An opening that lies on a broken-open hole** (`access.hole_covered`, `INFO`): a slot or window the size of a hole's breakout whose mouth lies inside that hole (a head channel cut across a slanted face) is that hole, and the hole's own path is judged.
- **Two mouths of one channel facing each other across a gap** (`access.mouth_sealed`, a question): what lies in the gap and touches both (a tube in a bearing bore the channel crosses) is asked as the assembly order, not failed as a seal. A clevis whose cheeks face each other across a tongue without a hole looks the same, so it is never passed.
- **A body that only clips the edge of a mouth** (`access.mouth_sealed`): the opening unit measures how the section fills in front of the mouth (`profile`). Full within the seal gap plus 0.25 (a plate flat on it), or full within one hole radius while it covers 0.3 of it at the mouth (a shaft lying across it): sealed. A body that covers a sliver at the rim and the whole section only farther out seals nothing; its distance is judged by the cover rules. Facts of an older unit hold only the share along the whole hit and are judged by it, as before.

Never close a finding by any of these:

- editing a number, a waiver, the triage list or the mode. Those are the owner's.
- renaming a body so that it is no longer found, or removing a hardware ref.
- taking a document, an STL folder or a .3mf out of `gate/layout.json`.
- changing a file under `gate/tools/` or `gate/rules/`.
- exporting the STL another way.

## Questions

Some rules cannot be checked by a script. The gate asks them, per changed part or per finding. A question about the whole part is asked only where it can apply: when the facts of the part prove that it cannot, the gate gives the answer itself and the report lists it under "Answered by facts". Such an answer is not yours and is not counted as attested. The proof is strict. Every unit the test reads must have facts for this geometry. A name can only make a question asked, never answered: a component named after its bearings, a bought body near under a name no pattern knows (the "Rotor" of a motor model) and a body that a hardware name picked and the shape refused all leave the question open. "Nothing recognised" is no proof: while the part has a screw hole, a slot, a hole a screw could use (up to `screws.any_hole_d_max`) or a bought body on an axis, the question is asked. What counts as near is `process.near_margin`; what counts as a motor or a connector is the name pattern `motors.ref_pattern`. `attest list` prints, per rule, what it asks and the answers it takes once, then one line per question; a line "the facts: ..." says why a question is asked here.

```bash
python3 gate/tools/gate.py attest list
python3 gate/tools/gate.py attest answer Q-51b0c2 --label "bed face is the modelled bottom; nothing faces down unsupported"
python3 gate/tools/gate.py attest answer Q-7c02aa --shot .shots/bracket_pocket.png
python3 gate/tools/gate.py attest answer Q-19ab04 --na "this part has no screws at all"
python3 gate/tools/gate.py attest answer Q-33c1d0 --param fits.sliding_per_side
```

Answer what is true, after looking:

- A **label** is one of the fixed answers, word for word. Pick the one that is true, also when it is the one that says "listed in the report for the owner". If none is true, do not answer: tell the owner. A label that the facts of the part contradict is refused: "this part has no screws" while the screw probe lists two, a washer, a screw that passes the part, or a screw hole with a bought body on its axis that nothing recognised (then read the row of `hardware.recognised` first). A "not applicable" that says the same thing is refused the same way. What only could be there refuses nothing: an empty hole a screw could use makes the question asked, and the answer is your word.
- An answer about the whole part holds while the facts do not contradict it. When a unit is run again for the same geometry and now shows what the answer denied, the question is open again (`attest list` says why), and a stamp that rested on that answer is stale.
- A **shot** is a screenshot of the changed zone, taken after the change and looked at. An old picture is refused.
- A **param** points at a number of this project with tag M (measured on a print) or U (owner decision). A number that is only decided (D) is not evidence, and a value of the declared target never is. For "what goes in this pocket" the parameter must be a fit and its value must be the diameter of that pocket: a pocket cut from a typed number is not covered by naming some parameter. With several declared targets add `--for <key>`.
- **na** needs the reason, in words that say something.
- You never type a free number, and you never answer for the owner. A question that only a waiver closes waits for him.

The export questions (`access.hole_supports`, `print.bed_face`) are asked when the new geometry is in no .3mf project yet. Answer from the model. Take a label that speaks of the sliced plate only when this geometry was sliced. Otherwise take the label that says the look at the slice is owed: the report lists it for the owner, and you do that look after the part is placed, before the print.

An answer is tied to the feature and its state. When the feature changes, the question comes back. A question about the whole part is asked again for every new geometry of that part: what is true of its screws and its surroundings changes with it. When a waiver behind an answer is withdrawn, the stamp that rested on it is open again. A stamp that rests on answers is `pass_attested`, and the report lists those answers for the owner: they are your statements, and he reads them.

## Before an export

```bash
python3 gate/tools/gate.py export demo/bracket
python3 gate/tools/gate.py export --generated stl/shim_05.stl
```

Export through the gate, never around it. It first scans the part's document (one short call), so it judges the model as it is now, not as the last run saw it; when something the part was checked against changed since (a neighbour moved onto a hole, a screw was replaced, the part itself), the export is refused with that reason and `gate.py run --changed` measures it again. That holds for an "already stamped" part too. It needs the design verdict to pass, writes the STL into quarantine, measures the mesh and its walls there, asks the export questions, and only then moves the file into the STL folder and writes the stamp. A part that fails stays in quarantine and the STL folder keeps the previous file. Its wall or mesh finding stays open: the next `run` shows it and exits 1 until the body is changed.

A part made by code (`--generated`) must be registered under `generators` in `gate/layout.json`. Use `--for <key>` when the project has several .3mf projects: a stamp is valid for the target it was judged for, and a part that goes into two projects is exported once for each.

Several parts can be named in one call. One export unit is one Fusion call with the unit budget of `gate/layout.json` (`"fusion": {"budget_s": 20}`); the parts that are left wait, the call exits 3, and the same command again goes on with them (`--wall` is the time of the whole command). A body with thousands of faces can use up that budget for its signature alone: then nothing is meshed, the answer says so, and that part needs a longer `budget_s`. Every export call writes a report: `report --last` shows the answers the new stamps rest on, the export questions included.

The stamp dies with the geometry. Any later change of the body needs a new run and a new export.

## Writing a .3mf

The .3mf writer (`bambu3mf.save`) asks the gate about every mesh it is about to write.

This costs time at every save, also a settings-only one and also in `observe` mode: the meshes of the archive and of the file on disk are parsed and hashed in pure Python. Count on about 5 to 15 s per million triangles per save (measured: 0.77 million triangles, 0.7 s without the gate, 4 to 12 s with it on Python 3.9); round parts placed in the same run can take several times longer. Nothing fails; a tool that saves more than once pays it each time.

- In `observe` mode it reports unstamped and stale meshes in one line and in `gate/reports/guard.log`, and writes the file.
- In `enforce` mode it refuses a new mesh without a valid stamp, and writes nothing.
- A mesh counts as carried (not judged again) only when a write event of the print ledger backs it (by its pose, the geometry of its source STL, or its vertex set under its own name: a weld or a repair) and that event names a stamp of the event's own geometry that still verifies for the declared target. The mode an event was written in proves nothing, and a stamp that went stale carries nothing in either mode. A mesh the guard found in the file on disk (`"tool": "outside"` in the ledger) never backs anything.
- A mesh that lies in the file on disk and that nothing backs (the owner's hand work, or older than the gate): in `observe` mode it is judged like in `enforce` when the save names its source STL (a build or a swap), and a valid stamp of that geometry backs it (a part exported since whose mesh did not change). The rest is let through, and every save says `N object(s) in <project> have no stamp: <names>`; so do the SessionStart and Stop hooks (with `"mark_unchecked": true` in `gate/project.json` the plates that hold one get the prefix `[unchecked] `; scripts find plates by name with the prefix taken off: `bambu3mf.plate_name`, `plates()`). In `enforce` mode it is judged like a new mesh and refused: also a settings-only save or a plain re-save of the file. A project goes to `enforce` once every part it prints is exported through the gate and swapped in.
- In `enforce` mode the file about to be written is also held against the declared target of its project (`project.settings_match`: the fit settings, the `"print"` block, per object too). A value that contradicts the target is refused; a key the target does not say is one loud line, and `verify` keeps it NOT_RUN.
- In both modes it compares the fit settings of the save (hole compensation, layer height, first layer height, the filament each object prints with and the rest of `target.fit_settings`) with the file on disk, global and per object. A change the caller did not name is refused in `enforce` mode and is one loud line in `observe` mode. A change that was named is printed in one line, never silent.
- A change is named by the tool that makes it (`set_project`, `set_settings`, `build`) or with `bambu3mf.note_setting`. A note lasts for one save, and it covers a change only when the new value is the one the declared target says (for that object under `"objects"`, else for the project). A note away from the target, or in a project with no declared target, is judged as not asked for: the owner changes the target first (`gate.py owner bundle` or a proposal).
- A .3mf written outside the gated tree (a scratch folder, /tmp, a download folder) is judged too when the writer finds the gated project for it: from the source STL of one of its meshes, from the working folder, from `CLAUDE_PROJECT_DIR`, or because a source STL is a byte copy of an STL of a gated project the hooks know. It counts as an unregistered project of that project: one loud line in `observe` mode; in `enforce` mode every mesh of it needs a valid stamp, and nothing of it is carried. `gate.py doctor` lists the scripts of the project that write a .3mf with `zipfile` themselves, past `bambu3mf.save`.
- A key that leaves the project's list of settings that differ from the system preset while its value stays is refused too: Bambu Studio takes the preset's value for a key that is not in that list. Set global values with `bambu3mf.set_project`: it lists the key.
- The guard remembers the fit settings of each project file in `gate/fit_settings.json`. A project that was deleted and is built again from a template is compared with what it held before. Commit that file with the project. When a file's settings changed since the last guarded save and no tool wrote them (Bambu Studio saved the project, or a file was copied over it), the next save says so in one line; `verify` is the check for it.
- In `enforce` mode a save is refused when the gate tools cannot be loaded at all.
- An object the owner declared outside the gate (`gate/owner/outside.json`, `owner outside` below) passes a save of its registered project, in both modes, only while its mesh in the archive about to be written has the geom_hash that was declared (the vertices as the .3mf stores them: moving it on its plate keeps it, a changed hole or a re-export does not). It gets no stamp and nothing of it is checked. Every save that holds one says `N object(s) in <project> are declared outside the gate by the owner ...: <names>`. Any other mesh under that name is judged like a new mesh: in `enforce` mode refused without a stamp, with the reason "changed since it was declared outside the gate: export it through the gate or declare it again". The same mesh under another name, a project that is not registered, and a copy outside the gated tree get nothing from a declaration. A broken `gate/owner/outside.json` lets nothing through (enforce refuses the save).

`python3 gate/tools/gate.py verify` checks a project without Fusion: every STL has a stamp, every STL is an object of some project, every object is on a plate and printable, every mesh matches a valid stamp, the project's nozzle is the one the stamps were judged for, and every object prints with the fit settings the declared target says (`project.settings_match`: its own override, else the global value), and with the print settings of its `"print"` block (`enable_support`, `support_type`, `support_remove_small_overhang`, `wall_sequence`; a target without that block is NOT_RUN: whether the overhangs print with supports is then compared with nothing). Run it before telling the owner a project is ready. An object that is meant to print with another value is declared by the owner under `"objects"` of the target in `gate/project.json`; an override nobody declared is a finding, and so is a declared one that a rebuild dropped. A value that equals the target while its key is not in the list of settings that differ from the system preset is told as one INFO row: the gate cannot read a preset, so check that key in Bambu Studio once. Other rules of the `bambu-project` skill stay as they are, first of all: never write a .3mf that Bambu Studio has open.

Supports and overhangs are decided by measurement, on the project as it is saved:
- `verify` measures each object as it lies on its plate (`print.overhang_angle`): down-facing faces flatter than `overhang.max_angle`, hanging ridges between steep faces, and faces that face straight down wider than `overhang.max_bridge`. With supports off they FAIL. With supports on, the slice decides, never the setting: every region is held against where the slicer put support (cells of 1 mm with their top, read from the G-code). A region with support under it is INFO; one the slicer leaves bare (its own threshold angle, "on the build plate only", manual supports) FAILs; a region narrower than one line prints from the layer below. No slice of this mesh, turn and settings: NOT_RUN, slice it. When the support setting cannot be read they are NOT_RUN.
- `python3 gate/tools/gate.py slice [PROJECT] [--changed | --all | --plates 1,4]` slices a COPY of a registered .3mf with the Bambu Studio CLI (`BAMBU_STUDIO` names it when it is not found), reads the support of every object from the G-code and stores it in `gate/run/slice/<key>.json`. A slice belongs to an object by its slice key: its mesh, the turn of its build item (a hand turn in the slicer) and the settings that move support. `--changed` (the default) slices only the plates where one of these changed. Each run works in a folder of its own and merges its plates into the record under a lock. It takes seconds to minutes per plate: run it in the background after every mesh swap, then `verify`.
- `print.slice_support_growth` (at `verify`) holds each object against its baseline in `gate/owner/support_baseline.json`, keyed by the object's name in its project. Never sliced, or sliced from another mesh: NOT_RUN. Support where the baseline has none, more than the share or the length over it, or ending higher: FAIL. An object with support and no baseline is NOT_RUN until the owner looks at the sliced plate and records it: `gate.py owner baseline PROJECT "OBJECT" --quote "..."` takes the numbers from the last slice, never from a typed value. `gate.py slice` writes what is waiting for that decision to `gate/proposals/support_baseline.json`.
- The bed face of a part (`print.z_layers`, `print.fit_axis`, `print.relief_layers`, `access.hole_closed`, `print.bed_face`) is measured on the saved project: the object whose mesh is the part's STL turned as a rigid body lies on the face that turn sends down. After an export the mesh still placed keeps its face, and its motion is remembered, so a later turn in the slicer moves the face too. A build table is read only for a project that does not place the part yet. `print.bed_face` is answered by the facts only when this geometry is the one placed.
- The guard says one line when a save brings a mesh whose support grew past its baseline, and it runs the overhang pre-check on every object the save brings: what hangs with supports off (or what a slice of that very mesh leaves bare) is loud in observe mode and refused in enforce mode. With `"slice_before_write": true` in `gate/project.json` (the owner's switch) it slices the changed plates of the archive inside the save (at most `"slice_timeout_s"`, 240 s per plate), and in enforce mode a support that grew, or a changed plate that cannot be sliced (no slicer on the machine, a timeout), refuses the save.

Walls and meshes are measured on the project as it is saved, too: `verify` runs the STL checks (closed, one shell, walls, slits, one-line walls) on the stored mesh of every object (`walls.placed_stl`). A part printed before the gate is judged like a new export, and its rows hold until it is exported again. A mesh is measured once and kept per pose hash in `gate/run/placed_walls/`; one `verify` measures for at most 20 s, the objects it did not reach are one NOT_RUN row, and the next `verify` goes on.

## Fits that were printed somewhere else

A fit counts only where it was printed: the same nozzle, material, hole compensation and layer height as the declared target.

- Parameters carry `measured_under` (see below). Table rows do too: every insert profile of `rules/tables/inserts.json` and the seat fit of `rules/tables/bearings.json`. An exact insert pocket of a row printed under other settings fails `inserts.pocket_shape` ("profile measured under other settings"), and so does a bearing seat when the seat fit records prints and none is this target's.
- `fits.decided_not_printed` is answered from the facts: one question per part that names every fit it relies on that is D or S here. "None" is refused while that list names anything.
- `python3 gate/tools/gate.py coupons --for KEY` writes the coupon plate of every such fit to `gate/proposals/coupons/KEY/`: one STL per coupon (an insert block, a magnet or pin pocket in three sizes, a tapered bearing bore and post, a box pocket) and `coupons.json`, which says what each hole is and how the result is recorded. Lay the STLs on one plate of that project with the Bambu tools, print, try the bought parts, and give the owner the result. He records it: a parameter with `owner param ... --tag M`, a print of a table row with `owner table` (below).
- Each coupon STL gets a coupon stamp (`gate/stamps/_coupons/KEY.json`): its geometry and the declared target of KEY. The guard lets the coupon plate into a project declared with the same target, in enforce mode too. A mesh counts as a coupon by its geometry only: a block named like a coupon is no coupon. A new `gate.py coupons` for the same KEY adds its stamps to those of the earlier runs, each with the target it was made for, so a coupon plate already in the project still saves after one of its fits is recorded.
- `gate/owner/tables.json` is his too. It holds what a project records of its own: the pins and screw lengths it stocks (`"pins": {"sizes": {"5": {"lengths": [...]}}}`, `"screws": {"stock_lengths": {"M3": [...]}}`), the bearings of the batch in hand, measured (`"bearings": {"measured": {"608": {"d", "D", "B", "source", "date"}}}`), and the prints of a table row (`"inserts": {"measured_under": {"M3x4x5": [{"nozzle", "material", "xy_hole_compensation", "layer_height", "source", "date"}]}}`, `"bearings": {"seat_fit": {"measured_under": [...]}}`). A row that cannot be read stops the gate (exit 4). It changes only through `gate.py owner table` (below), never by hand.
- A row of the tables re-judges only the checks whose judge read that table (each judged row keeps `tables_read`): a stock list of pins opens no insert check.

## Pins, pockets, bearings and screws

- A hole with a steel pin, dowel or rod on its axis (its own name matches `fits.pin_ref_pattern`) is that pin's pocket (`fits.bought_part_pocket`): its diameter is the press, slip or running fit of the pin, the fit's parameter is M or U here, the pin is a stock length of `rules/tables/pins.json` and longer than a blind pocket. Name pin refs with their size ("pin D5 x 20"): a name without a length is NOT_RUN. "No bought part goes in" is refused while a bought body stands on the axis.
- A slot or window of the size of a box kind of `rules/tables/pockets.json` (a board, a switch, a plug channel, a nut slot) is that pocket and needs its fit too.
- Bearings: with `bearings.seat_form` "tapered" (the owner's choice) a straight seat fails. A washer clamp has its own room (`bearings.clamp_room_washer`), apart from a printed clamp. `bearings.insertion_path`, `bearings.no_plastic_in_clamp`, `bearings.sleeve_end_and_preload` and `bearings.shaft_sleeve` are judged from the bearing facts: a wall on the way in closer than the pass clearance, printed plastic under the clamp screws, a sleeve end in the clamp path, a bought shaft of the bore size.
- Fit holes print upright (`print.fit_axis`): an insert pocket, a pocket or pin pocket of a bought part and a bearing seat lie within `print.fit_axis_deg` of the print axis, and a blind one opens upwards. A melt relief along the print axis prints `inserts.relief_depth_min` to `max` deep in the target's layers (`print.relief_layers`). A part no project places yet gets one INFO row for each; `print.bed_face` is asked at its export. A part that two registered projects lay on different faces is judged on each face, and the worst decides. An export judges the geometry it writes: when the project still places an older STL of the part, the face comes from that placement and `print.bed_face` is asked (exit 2): answer it and export again. The second export judges the STL the first one left in quarantine (the same signature and job): Fusion is not asked for it twice. `status` and `run` name the parts that were never exported through the gate, whose first export can stop so. A build item that scales, shears or mirrors an object is refused in enforce mode (observe says it in one loud line): set the scale back to 100 % in the slicer, or export the size you want.
- Two bearings on one axis (`bearings.spacer_room`): only one stack (inner or outer rings) is a fixed length that touches both rings; the other leaves at least `bearings.clamp_room` at its rings. A tapered seat (`bearings.seat_form` "tapered") ends in a `bearings.seat_lead_in` x 45 chamfer where the ring enters, measured where the seat wall ends; with "any" a straight seat more than `bearings.seat_taper_tol` off nominal is an INFO row. A clamp washer reaches `washers.ring_overlap_min` over its ring. A cover is taken for a stacked bearing by the designation in its name only when the name is no spacer, shim, sleeve, washer or ring.
- The swing of an L key (`access.key_swing`) sorts what blocks each direction as the screw path does: the part itself is a FAIL, another solid body one assembly-order question for the part, a mesh, box or hidden body NOT_RUN. A swing measured with another key (long arm, short arm, side clearance) is NOT_RUN.
- Screws: `screws.family_lengths` (the family of `screws.family`, a stock length, the name says the modelled length), `screws.head_recess` (a counterbore is the head plus 0.5 to 2), `screws.head_seat_full_ring` and `hardware.refs_present` (an insert pocket without its insert ref, a screw hole without its screw, a screw in no hole) are block rules. `access.key_swing` measures the swing of the long arm of an L key over every head (fusion_openings); a head with facts of an older unit is NOT_RUN until the part is run again.

## What only the owner decides

These files are his: `gate/owner/params.json`, `gate/owner/waivers.json`, `gate/owner/triage.json`, `gate/owner/tables.json`, `gate/owner/outside.json`, `gate/project.json`. Do not edit them, also not through a script. They change only through `gate.py owner ...`. The rules of `templates/gate/settings.json` in the project's `.claude/settings.json` deny agents any direct edit of these files (no prompt) and let `gate.py owner` ask once; while they are missing, `gate.py owner` refuses to write and `doctor` says so. Only he adds them. Every owner command needs `--quote`:

```bash
python3 gate/tools/gate.py owner waive F-9c1e04 --reason "the bore of the bought bearing is 1.8 mm away and cannot move" --quote "leave these two as they are"
python3 gate/tools/gate.py owner param inserts.wall_target 4.0 --tag U --source "owner, in chat" --quote "four millimetres everywhere"
python3 gate/tools/gate.py owner decide T-0003 tolerate --quote "fine for this print"
python3 gate/tools/gate.py owner decide G-5d0c1a tolerate --quote "all of these have held for a year"
python3 gate/tools/gate.py owner adopt --quote "take the model as it is today"
python3 gate/tools/gate.py owner table inserts M3x4x5 --under main --source "coupon plate of 2026-03-02, the inserts went in" --quote "the inserts fit"
python3 gate/tools/gate.py owner table pins 5 --value 16,20,32 --source "the stock box" --quote "these are the pins I have"
python3 gate/tools/gate.py owner outside main "Wrist gear" "Wrist spacer" --reason "from the older wrist document, which the gate does not register yet" --dry-run
python3 gate/tools/gate.py owner outside main "Wrist gear" "Wrist spacer" --reason "from the older wrist document, which the gate does not register yet" --quote "<his words>"
```

- Run one only after he said so in this conversation, and put his own words in `--quote`.
- A waiver needs a reason that says why the feature may stay. "Yes, export" is an order, not a reason, and is refused.
- A waiver holds for one feature in one state. When the feature changes it expires, and you ask again.
- A number looser than the registry default needs tag M or U. You may propose one; you may not set it.
- A fit is measured only where it was printed. `owner param NAME VALUE --tag M` stores a fit with the nozzle, material, hole compensation and layer height of the project it was printed from (`--under KEY` when several are declared). It is refused while that project file does not hold the values its target declares: the coupon was printed from the file, so run `verify` and put the two in step first. For any other project the fit counts as D, and `params explain NAME` says why. One size of a parameter (`--key`) cannot be M while its base value is not.
- `owner table TABLE [ROW]` writes one row of `gate/owner/tables.json`: `inserts KIND` and `seat_fit` record a print of that row under the declared target of `--under KEY` (refused while that project file does not hold the values its target declares, as for `owner param --tag M`); `bearings DESIGNATION --value d,D,B` a bearing of the batch in hand, measured; `pins D`, `screws M3` and `screws_set M3` with `--value` the stock lengths. `--source` says where it comes from. A row has one key: `5.0` is stored as `5`, `M3.0` as `M3`, a bearing alias as its designation, and the command replaces the row under any other spelling (a file that names one row twice stops the gate). The whole file is checked as the registry reads it before it is written, and the command and its quote are kept under `"_records"`. `--dry-run` prints the change and writes nothing (no quote needed).
- `owner outside PROJECT OBJECT... --reason R` declares objects of the registered .3mf project PROJECT outside the gate: parts of a document gate/layout.json does not register, which can never get a stamp, so that in `enforce` mode the file can be saved at all. It writes `gate/owner/outside.json`: per object the geom_hash of its mesh as the saved file holds it at this call, its triangles and plate, the reason, the quote, the date and the sha256 of the file (a name declared again keeps the old hash under `"was"`). It is refused for a name the file does not hold, or holds twice with different meshes, and for an object that IS a part of the gate: tied to a part of the census or a registered generator by a write of the journal, by its geometry or by the name of its STL, or named like one. Such a part is exported through the gate (`gate.py export`), never declared. Run `--dry-run` first (no quote needed): it prints the change and a `bundle entry` line. From an agent session the real call needs that dry run of the same project, objects and reason, with the file unchanged since, and a quote from a turn of his after it: a save of the file in between needs a new dry run. In a bundle the entry is `{"kind": "outside", "project", "objects", "reason", "expect": {object: geom_hash}}` (copy the `bundle entry` line): the apply is refused when a mesh is no longer the one in `expect`. `status`, `verify` (`OUTSIDE` lines; `project.mesh_unstamped` says such an object as INFO while its mesh is the declared one, FAIL once it changed) and the SessionStart and SubagentStart hooks list the declared objects in one line per project, with those that changed since.
- A pocket for a bought part (a magnet) whose fit is D is not exported (`fits.bought_part_pocket`). Print the coupon first: a small block with the pocket in three sizes, in the real material, from the real .3mf project. Its depth along the print axis is a whole number of layers, and its faces lie where a layer ends, counted from the first layer height of the target (`print.z_layers`).
- To propose: write `gate/proposals/<name>.json` and show him the rows. Give the measured value, the limit, what stops the fix, and what the choices cost.
- Switching `mode` to `enforce` is his decision too.
- The quote is checked. With the plugin's hooks on, a `gate.py owner ...` call goes through only when every `--quote` is the owner's own words in this session: his whole newest turn, or a piece of one of his turns of at least 12 characters and two words (whitespace and quote marks aside), or the answer he clicked in a question card. Text of an agent, of a subagent's task, of a workflow's computed task, of a task notification or of another session never counts. Quote what he typed, not your summary of it.
- Run it as a plain `python3 gate/tools/gate.py owner ...` command. When the quote holds, the hook leaves a one-time ticket for exactly those arguments; `gate.py owner` from an agent session refuses without one (`python3 -m gate`, an import of gate.py, a script file that calls it, a call more than five minutes after the check). In his own terminal the owner needs no ticket. Options are written in full (`--quote`, not `--quo`).

### Many decisions in one yes: `owner bundle`

When a pass needs several of his decisions (parameters, declared targets, waivers, triage decisions, the mode), prepare them as one proposal and ask once:

```bash
python3 gate/tools/gate.py owner bundle gate/proposals/2026-03-04-bundle.md --dry-run        # writes nothing, needs no quote
python3 gate/tools/gate.py owner bundle gate/proposals/2026-03-04-bundle.md --quote "<his words>"
```

The dry run prints what every entry does and the exact change of every file (a unified diff, `gate/owner/bundles.json` too); show it to him. The real call goes through only after a dry run of the same, unchanged proposal, and only with a quote from a turn of his that came after that dry run: change the proposal, and he sees a new dry run. The real call applies every entry with the owner commands above under his one quote: either every entry holds and the files are written, or one is refused and nothing is written. An applied bundle is kept in `gate/owner/bundles.json` (date, quote, path and sha256 of the proposal, the entries).

The proposal is a `.json` file, or a Markdown file (the text for him, in his language) that holds the bundle in one fenced block tagged `json gate-bundle`:

```json gate-bundle
]}
```

- `param` takes the fields of `owner param` (`key`, `under` optional); `target` sets (and with `unset` removes) keys of the declared target of a registered .3mf project, or of one object of it under `"objects"`, a `"print"` block merged key by key; `waive`, `decide` and `adopt` are the owner commands of the same name; `baseline` is `owner baseline`, with `expect` holding the numbers he is shown (copy the `bundle_entry` that `gate.py slice` writes into `gate/proposals/support_baseline.json`: the apply is refused when the slice record moved since); `table` is `owner table` (`row`, `value`, `under` as there; `value` a list or a text); `outside` is `owner outside`, with `expect` the meshes the dry run of `owner outside` shows; `mode` is `observe` or `enforce`; `deps` is `wide` or `tight` (tight is refused while `gate/run/*/deps_shadow.jsonl` holds a violation, no unit, or no unit with the same facts for fusion_near, fusion_gap or fusion_screws). `why` is never applied: it is the evidence he reads.
- Every entry is checked as the single command checks it (a looser number needs M or U, a fit tagged M needs the project it was printed from, a waiver needs an open finding and a reason that is not an order), and the end state as a whole is checked once more. `gate/project.json` is written last.
- Write the bundle; never apply it without his quote. Applying it is his yes, word for word.

## Rules and numbers

- The rules are in the plugin's `rules/registry/<category>.json`, vendored to `gate/rules/`. Each has a level: `block` (a check exists and stops the stamp), `attest` (a question), `advice` (text only; apply it by hand and say that you did or did not).
- A number is a parameter with a default, a unit and a tag. `python3 gate/tools/gate.py params explain inserts.wall_target` says where this project's value comes from and which rules read it.
- A new lesson becomes a rule in the registry of the plugin, with a judge fixture when it blocks. It does not go into a project file as prose. See the plugin's CONTRIBUTING.md.
- A rule that seems wrong for this project: tell the owner. The triage decision `rule_wrong` exists for that. Do not work around the rule.

## When the gate itself is in trouble

`python3 gate/tools/gate.py doctor` checks the interpreter, the vendored copy against `gate/LOCK.json`, the registry, the parameters, the project files, and one short ping to Fusion (a one-line read-only script with a 5 s limit: only a script that comes back shows that Fusion can run a check). It also lists every .3mf and every folder of STL files in the tree that `gate/layout.json` does not name, a document without motion groups, a key of `"stl_names"` that names no part of the last scan, a part whose STL path changed in the layout since the scan (scan again), a map the scan refuses, a file that two parts name as their STL, and missing ask rules.

- **forked**: a file under `gate/tools/` or `gate/rules/` (or the ledger tools beside them) differs from the lock. This blocks every command that judges, stamps or writes: `run`, `scan`, `export`, `verify`, `attest answer` and `owner` exit 4. `doctor`, `status`, `rules`, `params`, `report`, `triage` and `attest list` still read. Move the change into the plugin and vendor again; do not edit the lock.
- **stale**: the installed plugin is newer than the vendored copy. A warning. `python3 ${CLAUDE_PLUGIN_ROOT}/tools/setup_project.py <dir> --update-tools` brings the new rules; a judge that changed re-opens only its own check.
- **Fusion does not answer**: commands that need Fusion exit 4. `status`, `verify`, `rules`, `attest` and `run --offline` still work. Do not call into a hung Fusion a second time with a script of your own. `gate.py run` itself is safe to call again: it sends nothing while the unit it sent is still working, and it takes that unit's result when it is there.

## Adding the gate to a project

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/tools/setup_project.py <dir> --gate
```

It vendors the tools and the rules, writes `gate/LOCK.json`, creates `gate/project.json` in `observe` mode, `gate/layout.json`, `gate/owner/params.json` and `gate/RULES.md`, and turns the print ledger on. It prints two things and writes neither: the permission rules for `.claude/settings.json` and the lines for `CLAUDE.md`. Show both to the owner; he adds them.

Then:

1. Check `gate/layout.json`: every Fusion document, STL folder and .3mf project of the project is there (`doctor` and `verify` list the .3mf files and STL folders it does not name; the empty template under `"templates"` is not listed while it holds no mesh). A generator is a script that computes a mesh itself, with no Fusion body behind it: a script that exports Fusion bodies is NOT one, and `gate.py export --generated` refuses an STL that came from Fusion. Check the declared target of each .3mf project in `gate/project.json` with the owner: nozzle, line width, material, and the slicer settings every fit is measured under (layer height, X-Y hole and contour compensation, elephant foot compensation, wall generator). `setup_project.py --gate` reads them from the file as it is saved that day; a value a tool write changed earlier is already wrong there. Declare `motion_groups` for each document in `gate/layout.json` (which components move together, for example `[{"key": "slide", "patterns": ["^Slide"]}]`): with none declared, the gap to moving neighbours is not checked for any part, and the report and `doctor` say so. A part is exported to `<stl_dir>/<part slug>.stl`. Where the project already has STL files under its own names, and a build table that reads them, give each such part its file in `"stl_names"` of the document: `{"Motor plate": "MotorPlate_rev3.stl"}`, the key being the part name exactly as the census shows it, or its part slug, the value a file name inside `stl_dir`. Without it `gate.py export` writes a second file that nothing reads, and `verify` lists the old one as unstamped for ever. The map takes effect with the next `gate.py scan` (an export scans first, so also with the next export), which prints one `STL` line for every part whose file changed and one `STL NAME` line for every key that matches no part. If an earlier export already wrote `<part slug>.stl` for a part you map now, delete that file once the mapped one is exported: nothing rewrites it, and after the next change of the part it is listed as an STL without a valid stamp. A bad map stops the gate with a message (also a value that is a generator's STL). A mapped file that is another part's is a `NAME CLASH` line of the scan (exit 4): the part stays in the census with the file it had, and the map has to change. The scan prints the same line for any file that two parts name as their STL, for example two documents that share one `stl_dir` and each have a part with the same slug. `doctor` names a key that matches no part, a slug key that is never read because the part also has an entry under its name, a map the scan refuses, a part that still has its old path, and a file in the STL folder that is the part's file in another letter case.
2. `python3 gate/tools/gate.py doctor`.
3. `python3 gate/tools/gate.py run --audit`, repeated while it exits 3. An audit blocks nothing: it records what the project already has as inherited findings, and it notes the geometry of each part it judged (the baseline). It asks no question. A row that could not decide (`NOT_RUN`) is not inherited: it stays open and the list says what makes it run.
4. `python3 gate/tools/gate.py triage --md` and give the list to the owner. Its first table has one line per group (the same kind of finding on every part: rule and cause), what is measured and wrong first, with the count, the parts and the measured range. For each group he chooses: fix, waive, tolerate, or the rule is wrong (`owner decide G-...` for a whole group, `T-...` for one row; `owner adopt` takes the audit over without deciding a row). An inherited finding with no decision, or with "fix", blocks the next export of its own part. One he decided to tolerate, to waive, or whose rule he called wrong does not: the part is exported, its stamp is `pass_attested` and names the check as `tolerated`, and the report lists it.

**An inherited part** is a part whose geometry is still the one the audit judged, and that has no stamp. Nothing about it changed, so `run`, `status` and `attest list` ask none of its questions: they count them as waiting. `run --changed` does not measure it again once the owner adopted the audit. It stops being inherited in two ways. It changes: the next scan gives it a new signature, every question is asked, and a feature that changed gives new findings, which are ordinary blocks. Or it is exported: `gate.py export` asks its questions (`attest list --part ID` shows them) and holds its undecided rows; with those closed it gets its stamp like any other part. The baseline of a part is written once. Running the audit again does not make a changed part inherited again: it is then judged as in an ordinary run. Once the owner has adopted an audit, only `gate.py owner adopt` adds to what is inherited: a part that an audit judges after that (a new part) is judged as in an ordinary run, its rows block, and they go into the proposal for the owner. A proposal entry counts only while the report of its audit lists the part: a proposal written by hand makes nothing inherited. Do not answer the waiting questions of forty parts ahead of time; answer them for the part you export. A mesh of an inherited part that is already in a .3mf project is let through by the writer while it lies there, and every save names it as having no stamp; once it comes in anew (a rebuild, a swap) in `enforce` mode, it needs its stamp.

## Reporting

Say per part: stamp written or not, the open findings, the answers the stamp rests on, the waivers used. Give the counts by verdict, not one number: a `NOT_RUN` is not a `FAIL`. Name the inherited parts as such: judged, not stamped. List the rules that are registered and not checked yet (`deferred` in the report): for those the gate proves nothing, and the old care applies. Never fold "not run" or "not verified" into "passed".
